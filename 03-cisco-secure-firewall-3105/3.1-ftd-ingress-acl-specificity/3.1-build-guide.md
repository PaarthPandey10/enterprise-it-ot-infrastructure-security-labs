# 3.1 – Infrastructure Build Guide: Ingress Routing & FTD Access Control Specificity

> A visual narrative documenting the diagnosis of ingress drop logic, the instantiation of FDM logical objects, and the explicit policy injection on a Cisco Secure Firewall 3105.

---

## Overview

This guide provides a comprehensive breakdown of troubleshooting Access Control specificity on a Cisco Secure Firewall 3105 Threat Defense appliance. It details the transition from identifying ambiguous ANY-to-ANY rule failures to enforcing strict routing intent using mapped logical objects, culminating in a successful ASIC deployment and un-NAT'd packet flow validation.

### 2. Act II: The ANY-to-ANY Ambiguity
During the initial ingress validation phase, we configured permissive Access Control rules utilizing broad ANY network parameters for both source and destination. 

![](../../screenshots/fw1_2_Page_07.png)
*The Access Control policy matrix displaying Rule 1 (`Inside_Outside...`) configured with a "Trust" action, spanning from `inside_zone` to `outside_zone` with broad `ANY` network parameters.*

![](../../screenshots/fw1_2_Page_08.png)
*Detailed inspection window of the broad Access Control rule configuration.*

However, this setup failed to allow ICMP traffic to route cleanly. This highlighted a known behavior in Firepower Threat Defense (FTD): overly broad ingress rules can be easily overridden by default Dynamic PAT drop behaviors or implicit deny matrices when strict routing intent is not explicitly defined by the administrator.

### 3. Act III: Network Object Instantiation & Explicit Policy Override
To enforce strict routing intent and bypass the ambiguous hardware drop logic, a targeted logical approach was required within the Firepower Device Manager (FDM). 

* A custom Network Object named `inside_subnet` was defined. 
* This object was rigidly bound to the `192.168.95.0/24` CIDR block, successfully representing the entirety of the internal Dell Precision 7560 engineering network segment. 
* The broad, ambiguous "ANY" destination parameters were stripped out of the Security Policy.
* Explicit routing contexts were injected, mapping the destination network directly to the `inside_subnet` object to confidently permit un-NAT'd ingress traffic across the hardware backplane.

### 4. Act IV: Hardware Deployment
With the logical configurations complete, the pending changes were staged and compiled. 

![](../../screenshots/fw1_2_Page_09.png)
*The deployment status window confirming successful compilation and synchronization with no pending changes remaining in the queue.*

### 5. Act V: Ingress Flow Validation
The final phase required definitive proof of hardware bypass and successful backplane routing. 

![](../../screenshots/fw1_2_Page_10.png)
*Windows PowerShell execution of `ping 192.168.20.100 -t` showing initial drop behavior followed by steady 32-byte replies averaging 2ms with a TTL of 128, confirming successful hardware routing.*
