# 3.4 – Infrastructure Build Guide: Security Intelligence Engine & Custom Blacklisting

> A visual narrative documenting the deployment of the Security Intelligence (SI) pre-filter, bypassing air-gapped feed constraints, and validating absolute early-stage ingress drops on a Cisco Secure Firewall 3105.

---

## Overview

This guide provides a comprehensive breakdown of deploying the Security Intelligence (SI) engine via the Firepower Device Manager (FDM). It details the workaround engineered to bypass cloud-feed limitations in an isolated lab environment by utilizing custom network objects to successfully validate the hardware's pre-filter drop mechanics.

---

## Workflow Steps

### 1. Act I: SI Activation & The Air-Gapped Feed Constraint
The primary objective was to deploy the Security Intelligence (SI) engine to dynamically drop malicious ingress traffic before it could be processed by the standard Access Control matrix. 

![](../../screenshots/fw4_Page_1.png)
*Initial configuration required enabling the SI feature within the FDM. However, attempts to populate the block lists with dynamic Cisco Talos threat feeds failed. Diagnostics revealed that the isolated, air-gapped nature of the lab topology prevented the firewall from communicating with Cisco's cloud update servers.*

### 2. Act II: Custom Object Instantiation
To bypass the air-gap constraint and continue with the validation of the hardware drop mechanics, a manual SI feed workaround was engineered. 

![](../../screenshots/fw4_Page_2.png)
*A custom Network Object named `simulated-hacker-ip` was instantiated within the logical FDM database. This object was strictly bound to the external Work Laptop's IP address (`192.168.20.100`) to act as the malicious source.*

### 3. Act III: Policy Binding & Hardware Deployment
With the custom attacker object created, it needed to be integrated into the active SI defense matrix.

![](../../screenshots/fw4_Page_3.png)
*The custom `simulated-hacker-ip` object was successfully injected directly into the Security Intelligence Network Block (Drop) list. This configured the SI policy to act as an absolute pre-filter drop mechanism for that specific IP.*

![](../../screenshots/fw4_Page_4.png)
*The configured SI policy was subsequently compiled and deployed. The pending changes were successfully pushed to the active ASIC routing engine without errors.*

### 4. Act IV: Ingress Drop Validation & Log Analysis
To validate the engine's efficacy, a simulated connection attempt was initiated to trigger the pre-filter drop logic.

![](../../screenshots/fw4_Page_5.png)
*ICMP Echo requests (ping) were initiated from the internal Dell Precision (`192.168.95.100`) targeting the simulated attacker IP. The requests immediately resulted in a "Request timed out" (100% loss) status, proving the connection was actively severed.*

![](../../screenshots/fw4_Page_6.png)
*Subsequent diagnostics within the FDM Event Viewer's Security Intelligence dashboard confirmed the traffic was successfully intercepted. The engine registered a definitive Block action against the initiator IP, validating that the SI pre-filter successfully vaporized the targeted traffic at the absolute earliest ingress phase, completely bypassing standard Access Control evaluation.*
